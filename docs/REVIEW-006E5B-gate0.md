## Blocking findings

1. **Fail-open if local cleanup throws or is absent.** `app/utils/auth.ts:384-392` silently swallows `signOut` exceptions and treats a missing `signOut` as success without checking storage. `processAuthCallback` then returns a failure at lines 503-509 / 575-582, yet persisted credentials may survive; `getUser()` on later route verification can admit a different identity. A scratch-only `vite-node` probe of actual `processAuthCallback`, `inspectLocalSessionState`, `resolveVerifiedUser`, and `checkRouteAccess` with an injected throwing `signOut` returned `{callbackFailed:true,persistedState:"confirmed_present",laterVerifiedId:"B",protectedAllowed:true}`. The installed SDK's `GoTrueClient._signOut` source (`node_modules/@supabase/auth-js/src/GoTrueClient.ts:4082-4117`) clears on handled HTTP 500, but it does **not** put `_removeSession` in an unconditional `finally`: an unexpected throw or session-read error before cleanup is not proven safe. Do not report blanket containment under unknown local state.
2. **Post-call missing response without containment.** `app/utils/auth.ts:492-498` and `:543-549` return on missing `data.session`/`data.user` without checking whether SDK storage was changed. A synthetic probe supplied an already persisted session while `exchangeCodeForSession()` returned `{data:{session:null,user:null},error:null}`; callback failed but storage stayed `confirmed_present`. This models an incomplete/contradictory SDK result; it is not evidence live Supabase emits one. Distinguish a genuinely pre-establishment failure (preserve older valid session) from an unknown post-call state rather than assuming missing response means nothing was stored.
3. **Browser hard-reload assertion doesn't cover protected SSR.** `tests/browser-diagnostic-006e5a.mjs:448-486` first observes the SPA redirect to `/?auth_required=true` and then calls `page.reload()` there. Thus it only reloads public home, not `/protected`. A scratch-only copy inserted `page.goto('/protected')` before reload and passed, but this independent coverage must be made executable in the checked-in harness. Positive control only logs the fresh-verification delta, not asserts it; the local-scope test has a conditional `if (logoutRequests.length > 0)` so it could pass without any logout request (`tests/diagnostic-006e5a.test.ts:308-316`).

**Independent second review:** A separate read-only reviewer confirmed the blocking swallowed/missing `signOut`, incomplete post-exchange response, public-page reload, and misleading unconditional SDK-cleanup claim. Its verdict also rejects closing Row A. The reviewer did not rerun tests; the execution numbers above are Hermes's own reruns. The old worktree was already dirty in other auth files, so `git diff --name-only app/` alone cannot establish a per-handoff change list; the protected-files baseline hash and scoped source comparison support the seam attribution.

**Conclusion:** the 006E5B change fixes the observed normal A/B mismatch, but the handoff explicitly required fail-closed behavior or a stop if local state was present/unknown under cleanup failure. The implementation neither checks it nor stops; do not advance to Row B. Keep a correction bounded by an executable failing cleanup-failure fixture and independent protected SSR assertion. If fail-closed behavior cannot be achieved within the agreed one production seam, stop and request a scope/policy decision instead of silently broadening production edits. Real-SDK event race, rendered callback success/auto-navigation and authorized live Google OAuth remain separate Gate 0 work.
