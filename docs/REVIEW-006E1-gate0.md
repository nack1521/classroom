## Independent browser reproduction — RED boundary

Used fresh built Nuxt server, controlled loopback Auth endpoint, and host-installed Playwright/Chromium with isolated browser contexts and synthetic cookies (no repository dependency added). Each case opened the **rendered** `?error=access_denied` callback, observed the error DOM/no protected success link/no automatic protected redirect, clicked Return Home, then deliberately clicked the protected link. The error-description marker was not visible.

- **Valid older session:** callback denied; home hydrated to authenticated status; the Auth stub had 2 verification hits by the time home was shown. Immediately **after home and before clicking** `/protected`, the stub was changed to reject that same previously valid token. The SPA click still reached `/protected`, displayed **“Authentication Verified”**, and made **zero new verification requests**. A hard reload of `/protected` then made a verification request and redirected to `/?auth_required=true`. Reproduced twice. This violates the agreed requirement to independently re-verify on deliberate protected navigation when a previously valid session has since become invalid. Root cause is consistent with `app/middleware/auth.ts:28-33`, which skips `checkVerifiedUser()` when `user.value?.signedIn` is already true; the browser probe establishes the outcome, not just the inference. It does not prove server-side data authorization is bypassed; the observed exposure is protected route/UI access with stale client auth state.
- **Absent older session:** callback denied; home visitor; SPA protected click redirected to `/?auth_required=true`, with no verified banner.
- **Forged older session:** callback denied; home visitor; protected click made a rejecting Auth request and redirected to `/?auth_required=true`, with no verified banner.
