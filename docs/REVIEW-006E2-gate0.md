# REVIEW-006E2 — browser RED regression for stale SPA auth

**Reviewed:** 2026-09-25; branch `fix/gate0-auth`. **Verdict:** The real-app RED symptom is independently confirmed and the diagnostic is useful, but the test runner is **not yet an acceptable durable regression gate** because its controls/cleanup do not meet the handoff. Gate 0 remains **not passed**. No production source, existing tests, dependencies, commit, push, deployment, or real account was changed in this review.

## Independent verification

- Inspected the untracked runner `tests/browser-diagnostic-006e2.mjs` and report. The protected five-auth-file diff hash remains `2b50de1002c41ef3d18bc0bc01b42ec61a96887a8e714a9473f3b3161538cb75`; `git diff --check` exited 0.
- Fresh `npm run build`, `npm run lint`, `npm run typecheck`, and `npm run test` exited 0. Vitest baseline: **87/87 across 6 files**. With the host Playwright module, the browser controls command exited 0; the browser RED command exited 1 **because the previously valid token was rejected after home hydration but SPA navigation made zero new `/user` requests, entered `/protected`, and showed “Authentication Verified.”** The same page's hard reload made a fresh request and redirected to `/?auth_required=true`. This matches the earlier independently written browser probe, not merely the IDE agent's summary.

## Findings requiring test-only correction

1. **Positive control is only a route-rendering control, not a verification control.** `tests/browser-diagnostic-006e2.mjs:200-219` records `delta = 0` for a still-valid token and marks PASS solely because the protected route and identity appear. The handoff required distinguishing fresh verification on navigation from cached `user.value`, so the required positive control would be RED too under the agreed contract. Labeling this a complete passing positive control overstates coverage. Retain a separate current-behavior control if useful, but add the intended policy assertion once the route fix is authorized.
2. **Runner leaks built-server processes.** `main()` calls `process.exit(0/1/2)` inside `try`/`catch` at lines 428, 435, 438, 449, 452, 456; this exits immediately rather than awaiting `finally { await cleanup() }` at lines 457-459. Five orphaned Classroom built-server processes existed before my rerun; two more appeared after controls/RED. I terminated those seven exact built-server PIDs and verified none remain. Do not run the runner repeatedly unattended until exit handling is corrected. Its `cleanup()` also invokes `stubServer.close()` without awaiting close completion.
3. **Hard-reload negative control is logged but not asserted.** Lines 346-397 collect `reloadDelta` and `reloadUrl`, yet the contract boolean only tests pre-reload values. A broken hard-reload path would still be classified as the same expected RED, obscuring a second regression.
4. **Startup and failure hygiene:** `startNuxtServer()` does not fail explicitly when its 7-second readiness loop expires; the next browser action may fail ambiguously. The generic `catch` prints the raw exception (`console.error(err)`), which can include URLs; avoid raw diagnostic payloads in logs. These are test harness issues, not evidence that the real-app reproduction is false.

**Decision:** Accept the independently reproduced *behavioral finding* and test-only scope adherence. Require a small **test-harness-only** correction for cleanup, readiness failure, and honest controls before treating this script as a durable gate or sending a production fix. Do not make the existing RED green by weakening the assertion; when the route guard fix is later authorized, both revoked and still-valid cases should show a fresh verification request and correct route outcome. Mismatch quarantine, SDK event race, callback success DOM, adjacent error surfaces, and authorized real Google OAuth remain separate Gate 0 boundaries.
