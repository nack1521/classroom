## Single question

When a user cancels a new Google OAuth attempt with `?error=access_denied`, does the *actual app path* deny this callback without silently revoking a separately valid older session, while allowing access to `/protected` only after a later **deliberate** navigation and independent verification? Distinguish the callback failure, persisted SDK session, UI identity, and route decision. The test must reach production `useAuth()` and production route middleware; `authGuard()` with a supplied boolean is not enough. Use a controlled loopback Auth endpoint and synthetic IDs only.

Assert the rendered error state has no protected success link and no automatic protected redirect. Assert denial does not call sign-out or assert remote revocation; inspect persisted session without printing it. After explicitly navigating to `/protected` (including a hard reload/request boundary if feasible), require the production middleware → `useAuth()` → request/browser SDK → `getUser()` chain to re-verify *that same older identity* before allowing access. Inspect public-page identity status after returning home/reload; do not claim “signed out” while a valid session remains.
