# Gate 0 workflow audit — why five corrective rounds occurred

**Reviewed:** 2026-09-25  
**Scope:** Classroom handoffs 001–005, independent reviews 001–005, current tests and implementation; no code or account changes in this audit. `HANDOFF-ANTIGRAVITY-006.md` was prepared but has not been submitted.

## Finding: shared responsibility, not a single bad actor

- **Hermes's early acceptance criteria were too permissive.** Handoff 001 asked for a minimal callback/session/guard and tests “where practicable” (`HANDOFF-ANTIGRAVITY-001.md:11,19-21`), but did not require authenticated SSR hard reload or a cookie-backed request boundary. Handoff 002 explicitly allowed a controlled server-client *mock/cookie* (`HANDOFF-ANTIGRAVITY-002.md:18`), which was not sufficient to distinguish a real adapter from a helper handed a boolean/mock. Handoff 003 said a real request boundary was needed, but its “at minimum” phrasing still permitted a stubbed endpoint/**client** rather than proving the production chain (`HANDOFF-ANTIGRAVITY-003.md:11-13`). These omissions contributed to rework. Hermes should have defined negative controls and the actual runtime seam before delegating.
- **Later briefs became materially explicit, but Antigravity's evidence sometimes did not meet them.** Handoff 004 explicitly required production middleware → `useAuth()` → cookie client → `getUser()` and a test that changes outcome when the cookie changes (`HANDOFF-ANTIGRAVITY-004.md:13-15`). The implementation instead supplied a hand-built `authContext` to the exported handler (`REVIEW-004-gate0.md:23`). Handoff 005 required in-flight sign-out verification, actual browser-client initialization and built-app request tests (`HANDOFF-ANTIGRAVITY-005.md:9-11`), but its result claimed complete scrubbing despite passing raw errors to UI, modeled remote sign-out failure without the installed SDK's `SIGNED_OUT` event, and allowed HTTP tests to pass without a build artifact (`REVIEW-005-gate0.md:16-22`). Those are implementation/verification failures, not just unclear wording.
- **The workflow made green checks too easy to overinterpret.** Tests grew from 17 → 26 → 33 → 38 → 45 while the same auth boundary exposed another failure after each independent review. Unit mocks, helper-only assertions, conditional test returns, and a missing real OAuth environment made “all tests pass” a weak claim. Hermes also reviewed *after* each full implementation rather than signing off on a red-capable test contract first. Antigravity's improvements are real—local built-app SSR cookie/request isolation and single-owner browser PKCE were independently checked in round 005—but they do not close all local auth behavior.
- **This is now an architecture/contract checkpoint.** Five correction rounds on one Gate 0 slice warrant stopping the automatic fix-and-retry loop. Resolve the ownership of PKCE exchange, state transitions on SDK auth events, local-vs-remote sign-out semantics, and safe error surfaces as a small explicit contract. Use the installed SDK with controlled local endpoints to observe behavior; do not build tests around an assumed SDK policy. Then write the minimal failing regressions *before* another production-code pass.

## Recommended change to delegation

1. **Do not submit the prepared four-part Handoff 006 as-is.** Its broad correction list invites one more all-at-once claim. Split into a diagnostic/test-only stage and a later implementation stage.
2. **Diagnostic stage:** Antigravity traces current source and installed SDK, writes/executes deterministic failing regressions for (a) exchanged new user vs old `getUser()`, (b) remote sign-out 500 with real SDK event/storage, (c) provider/SDK error containing a synthetic sensitive marker, and (d) absent/stale built app cannot silently count HTTP integration as passed. No production auth edits, deployment, or real accounts. It reports exact red results and stops.
3. **Hermes review gate:** independently verify the tests actually reach production seams, choose an explicit local/remote sign-out and callback identity contract, and decide if a smaller architectural simplification is needed. If the repros are wrong or cannot be made deterministic, fix the test/contract rather than guessing at auth code.
4. **Implementation stage:** one narrowly scoped correction at a time (red → green), then full checks and independent SDK/built-app probes. Only after the local contract passes is it sensible to ask Nack to test an authorized Google school account. Do not send credentials through chat.

**Responsibility statement:** Hermes owns the ambiguous early test gates and the choice to continue patching after multiple misses. Antigravity owns the later code/test/report mismatches against explicit criteria. No evidence here proves the IDE agent is categorically poor at coding; this particular auth/SSR/OAuth task is complex and the handoff+verification loop needs a tighter contract.
