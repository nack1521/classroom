# Gate 0 auth policy — agreed contract

**Decision:** 2026-09-25, Nack accepted Hermes's proposed policy in chat. **Gate 0 auth spike PASSED in the agreed time-boxed local scope on 2026-09-26**; see `docs/REVIEW-006F1-gate0.md`. This contract and sign-off do not authorize a commit, deployment, or real student data. Broad `HANDOFF-ANTIGRAVITY-006.md` remains HOLD.

## Distinct callback outcomes

1. **Provider cancellation/denial** (e.g. `access_denied`): fail this callback attempt; show a safe notice and no success/protected continuation or automatic protected redirect. Do **not** silently sign out an independently valid older session. If the user later deliberately navigates to `/protected`, production middleware must re-verify that session; allow only if it verifies. Make the displayed identity/current-session status honest, including after returning home or reloading. Callback denial is not evidence of session revocation.
2. **New callback identity mismatch, missing identity, or unverifiable established identity**: fail closed; do not surface the old or new identity as successful, and do not let an ambiguous SDK session silently regain protected access via middleware. Require a fresh verified, unambiguous sign-in before protected continuation. If implementation chooses to clear a local session, use local scope only, never an implicit global sign-out of other devices; do not claim remote revocation or local removal when unconfirmed. Exact mechanism follows SDK characterization/test evidence, not an assumed mock result.
3. **Successful exchange/setup:** the established session user, response user, and independently verified user must agree; show the verified identity and allow protected navigation only after success. Test the rendered success DOM and actual redirect, not only a helper return value.

## Error exposure

All user-visible auth errors, including initialization, auth-state events, Google sign-in result/throw, and callback, must use fixed safe categories rather than raw provider/SDK `message`/`error_description`. Do not leak synthetic code/token markers through UI or logs; keep enough generic guidance for retry. Do not weaken or overwrite the already accepted callback-only 006D behavior.

## Evidence before implementation

Test provider denial with valid and invalid older sessions through `useAuth()` and production route middleware, including deliberate protected navigation; test mismatch as a separate fail-closed case. Test a real SDK `SIGNED_IN` event whose deferred verification has actually started before denial/sign-out/race resolution; pure helper events and direct `checkVerifiedUser()` do not establish this. Test both rendered callback failure and success branches with synthetic loopback responses. Include positive controls and a diagnostic RED assertion for each missing contract; diagnose SDK behavior before selecting a production fix. Then authorize one narrow red-to-green change at a time. The authorized end-to-end Google OAuth pilot with a school-managed account was owner-reported successful and recorded in `docs/GATE0-LIVE-PILOT-CHECKLIST.md`; no credentials, tokens, or real student data in chat/repo.

## Gate 0 time-boxed evidence boundary (Nack go-ahead, 2026-09-26)

The behavioral rule above remains fail-closed for the supported, installed Supabase SDK and actual browser/cookie adapter. Gate 0 requires ordinary mismatch containment, valid/denied callback controls, real-SDK event-race and rendered successful callback evidence, and an authorized live Google OAuth pilot. If a cleanup failure with persisted ambiguous session is **reproducible using the installed SDK and actual cookie/storage adapter**, reopen Gate 0. Five 006E5C fault-injection contracts (forced throw before removal, artificial missing method, artificial incomplete SDK response after manually persisting) plus the 006F A2 custom cookie adapter that intentionally ignores deletion remain visible and runnable as **six RED hardening stress cases**, not silently relabeled GREEN or removed; their injected shapes alone are not evidence those outcomes occur in the supported integration and do not automatically block this time-boxed Gate 0. A future product/release gate must revisit them if the integration or threat model changes. Unverified adapter failure is a disclosed limitation, not a PASS or evidence that deletion always succeeds.
